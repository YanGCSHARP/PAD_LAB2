# Архитектурные решения

## 1. Декомпозиция

Границы сервисов проведены по бизнес-возможностям (bounded contexts). У каждой границы свой владелец данных:

| Контекст | Владеет данными | Почему отдельный сервис |
|---|---|---|
| Identity (auth) | учётные записи, хеши паролей, refresh-токены, ключ подписи | чувствительные данные изолированы. Сервис отвечает только на вопрос «кто это» |
| Profiles (user) | профиль: имя, телефон, город | меняется независимо от учётной записи. Нагрузка — чтение |
| Catalog | площадки, мероприятия, категории, остатки, резервы | источник правды по наличию билетов. Нагрузка на чтение афиши самая большая, сервис масштабируется отдельно |
| Booking | брони и их жизненный цикл | ведёт процесс покупки. Его состояние нельзя смешивать с каталогом |
| Payment | платежи, возвраты | интеграция с внешним провайдером. Свои требования к аудиту и безопасности |
| Notification | уведомления, проекция контактов | побочный эффект. Не должен влиять на основной поток: асинхронный и устойчивый к сбоям |

**Database-per-service**: 5 отдельных контейнеров PostgreSQL и MongoDB, у каждой БД свои учётные данные. Ни один сервис не читает чужую БД. Данные других контекстов приходят только через API или события, например booking хранит копию `event_title`, а notification — копию email пользователя.

## 2. Синхронное и асинхронное взаимодействие

| Взаимодействие | Тип | Почему |
|---|---|---|
| Клиент → Gateway → сервис | REST | клиенту нужен немедленный ответ, OpenAPI-контракт |
| booking → catalog (резерв) | **gRPC** | клиент должен сразу узнать, получил ли он билеты: это нужно синхронно и атомарно. Строгий контракт и deadline |
| auth → user (профиль) | событие | регистрации не нужно ждать создания профиля. Если user-service недоступен, регистрация всё равно проходит |
| booking ↔ payment | события (сага) | оплата долгая, ненадёжная и внешняя. Её нельзя держать внутри HTTP-запроса |
| * → notification | события | уведомления — побочный эффект. Их сбой не должен ломать покупку |

## 3. Сага покупки (хореография)

Состояния брони: `PENDING_PAYMENT → CONFIRMED | CANCELLED`.

| Шаг | Сервис | Действие | Компенсация |
|---|---|---|---|
| 1 | booking | gRPC `ReserveTickets` (атомарно уменьшает `available`) | `ReleaseTickets` |
| 2 | booking | бронь `PENDING_PAYMENT` + `booking.created` (одна транзакция) | при ошибке commit сразу вызывается `ReleaseTickets` |
| 3 | payment | списание → `payment.succeeded` / `payment.failed` | возврат денег (`payment.refunded`) |
| 4a | booking | `ConfirmReservation`, `CONFIRMED`, `booking.confirmed` | — |
| 4b | booking | `ReleaseTickets`, `CANCELLED`, `booking.cancelled` | — |

Гонки и порядок событий:
- Пользователь отменил бронь до прихода `payment.succeeded`: booking игнорирует платёж (бронь не в `PENDING_PAYMENT`), payment получает `booking.cancelled` и делает возврат.
- `booking.cancelled` пришёл в payment раньше `booking.created`: payment создаёт запись `CANCELLED`-заглушку, и последующий `booking.created` не приводит к списанию.
- Все gRPC-методы catalog идемпотентны по `booking_id`, поэтому повтор шага безопасен.

## 4. Transactional outbox

Проблема двойной записи: «сохранили бронь, но не отправили событие», или наоборот.
Решение (`libs/common/common/outbox.py`):

1. Сервис в одной транзакции пишет бизнес-изменение и строку в таблицу `outbox`.
2. `OutboxRelay` (фоновая задача) раз в 0.5 с выбирает неопубликованные строки (`FOR UPDATE SKIP LOCKED`, чтобы несколько реплик не мешали друг другу), публикует их с publisher confirms и проставляет `published_at`.
3. Если RabbitMQ недоступен, строки остаются, relay повторяет попытки с экспоненциальной задержкой. Сервис продолжает принимать запросы.

Гарантия — at-least-once. Дубли закрывает идемпотентность потребителей.

## 5. Идемпотентность

| Где | Механизм |
|---|---|
| Потребители в PostgreSQL | таблица `processed_events(event_id PK)` пишется в той же транзакции, что и эффект обработчика |
| notification (MongoDB) | уникальный индекс `event_id`. Статус `pending → sent` позволяет повторить отправку после сбоя |
| payment | `UNIQUE(booking_id)`: одна бронь — один платёж, даже если пришёл новый `event_id` |
| catalog gRPC | `reservations.booking_id` — первичный ключ |
| `POST /api/bookings` | заголовок `Idempotency-Key`, `UNIQUE(user_id, idempotency_key)`. Повтор возвращает ту же бронь с кодом 200 |

## 6. Отказоустойчивость

| Сбой | Поведение |
|---|---|
| сервис не отвечает | Gateway: timeout 5 с → **504**. gRPC deadline 3 с → **504** |
| сервис недоступен (connection refused) | **503**. GET повторяется (2 retry, backoff 0.2/0.4 с), POST — нет |
| сервис падает постоянно | **circuit breaker**: после 5 ошибок подряд цепь открывается на 15 с, запросы сразу получают 503 `circuit_open`, потом пробный half-open запрос |
| бизнес-отказ из gRPC (sold out) | не считается сбоем для breaker'а, отдаётся 409 |
| БД недоступна | `/ready` → 503, ошибки SQLAlchemy → 503 `database_error`, `pool_pre_ping` и таймаут подключения 5 с |
| RabbitMQ недоступен | при старте — до 30 попыток подключения. В работе события копятся в outbox, `connect_robust` переподключается и восстанавливает подписки |
| обработчик события упал | повтор с backoff (0.5, 1, 2, 4, 8 с), после 5 попыток — `<queue>.dlq` |
| битое сообщение | сразу в DLQ |
| Redis (rate limiter) недоступен | fail-open: запрос пропускается, в лог пишется warning |
| auth-service недоступен | сервисы продолжают проверять токены по закэшированному JWKS. Если ключа ещё нет — 503 |
| часть данных для `/api/dashboard` недоступна | ответ всё равно отдаётся, недоступная часть перечислена в `degraded` |
| необработанное исключение | 500 `internal_error`, traceback пишется только в лог |

## 7. Безопасность

- RS256: приватный ключ есть только у auth-service, остальные знают лишь публичный. Скомпрометированный сервис не сможет выпускать токены.
- Refresh-токены одноразовые. В БД хранится только SHA-256 токена.
- bcrypt (12 раундов) выполняется в thread pool и не блокирует event loop.
- Rate limit на `/login` и `/register` — 20 запросов в минуту с одного IP (защита от перебора). Общий лимит — 300 в минуту на пользователя или IP.
- Контейнеры работают от непривилегированного пользователя `app`.
- Секреты передаются через переменные окружения (`.env` не коммитится, есть `.env.example`).

## 8. Масштабирование

- Сервисы stateless (состояние в БД), запускаются репликами: `docker compose up --scale catalog-service=3`.
- Конкурирующие потребители одной очереди распределяют нагрузку. Outbox relay безопасен при нескольких репликах благодаря `SKIP LOCKED`.
- Rate limit хранится в Redis и поэтому общий для всех реплик gateway.
